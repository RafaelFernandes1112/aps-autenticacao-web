## 1.6 Servidor de aplicação
 
O servidor de aplicação é o componente que executa a lógica do software. No ambiente adotado, ele é formado pela aplicação Spring Boot, que reúne o Spring MVC e os componentes da API de Autenticação. Em vez de instalar um servidor separado e implantar a aplicação nele, a própria aplicação é empacotada em um arquivo JAR executável que já contém o Tomcat (item 1.5) e todas as bibliotecas de que precisa. Ao ser iniciada com o comando java -jar, a aplicação cria o contexto do Spring, instancia e conecta os componentes AuthController, AuthService, UserRepository e PasswordEncoder (item 2.1.3), configura o acesso ao banco de dados e executa o script schema.sql, que cria a tabela usuario caso ela ainda não exista (item 1.7). Só então o Tomcat passa a aceitar conexões na porta 8443 (SPRING, 2026).
 
O servidor de aplicação é invocado a cada requisição entregue pelo Tomcat. A requisição chega ao DispatcherServlet, o controlador frontal do Spring MVC: um ponto de entrada único que delega o trabalho a componentes configuráveis, começando pelo mapeamento que identifica qual método da aplicação trata a combinação de método e caminho recebida, no caso de POST /api/login, o método login do AuthController. Antes de chamá-lo, o Spring converte o corpo JSON da requisição em um objeto LoginRequest, com o identificador e a senha, usando a biblioteca Jackson, e valida esse objeto com o Bean Validation. Se o JSON estiver malformado ou algum campo estiver ausente ou vazio, o método não é chamado e a resposta é 400 (Bad Request) (SPRING, 2026).
 
Com os campos válidos, o método executa a lógica de autenticação, cuja organização em componentes é descrita na Seção 2 (itens 2.1.3 e 2.2). O AuthService normaliza o identificador, removendo os espaços nas pontas e convertendo-o para minúsculas; o UserRepository busca o usuário pelo login ou pelo e-mail no SQLite, embutido no mesmo processo (item 1.7); e o AuthService compara a senha informada com o hash BCrypt armazenado, por meio do BCryptPasswordEncoder (item 2.1.6). Quando o usuário não existe, a comparação é feita com um hash fictício, gerado na inicialização, para que o tempo de resposta não revele se o identificador está cadastrado. Usuário inexistente e senha incorreta produzem a mesma exceção de autenticação (RNF03).
 
O resultado do processamento é a resposta HTTP. Em caso de sucesso, a identificação do usuário é convertida de volta para JSON, com os campos id e nome, e enviada com o código 200 (OK); em caso de falha de autenticação, o tratador de exceções do AuthController produz o código 401 (Unauthorized), com uma mensagem genérica de erro no campo erro (item 1.4). A resposta é devolvida ao Tomcat, que a envia ao navegador pelo canal seguro (item 1.5). Além da resposta, o Spring Boot registra em log os eventos de inicialização e eventuais erros internos; a senha nunca é escrita em log nem devolvida em nenhuma resposta (ANTHROPIC, 2026d).
