## 1.6 Servidor de aplicação
 
O servidor de aplicação é o componente que executa a lógica do software. No ambiente adotado, ele é formado pela aplicação Spring Boot com o servidor Tomcat embutido: em vez de instalar um servidor separado e implantar a aplicação nele, a própria aplicação é empacotada em um arquivo JAR executável que já contém o Tomcat. Ao ser iniciada com o comando java -jar, a aplicação cria o contexto do Spring, configura automaticamente o Spring MVC e sobe o Tomcat, que passa a escutar requisições HTTP na porta 8080 (SPRING, 2026a). Como essa porta é acessível apenas pela rede interna, o servidor de aplicação só recebe requisições repassadas pelo servidor web (item 1.5).
 
O servidor de aplicação é invocado a cada requisição encaminhada pelo Nginx. O Tomcat aceita a conexão, interpreta a mensagem HTTP e atribui o seu processamento a uma thread do seu pool, de modo que várias requisições podem ser atendidas em paralelo. Em seguida, entrega a requisição ao DispatcherServlet, o controlador frontal do Spring MVC: um ponto de entrada único que delega o trabalho a componentes configuráveis, começando pelo mapeamento que identifica qual método da aplicação trata a combinação de método e caminho recebida, no caso, POST /api/login (SPRING, 2026b).
 
Antes de chamar esse método, o Spring converte o corpo JSON da requisição em um objeto Java com o identificador (login ou e-mail) e a senha, usando a biblioteca Jackson (SPRING, 2026a). O método executa então a lógica de autenticação, cuja organização em componentes é descrita na Seção 2 (itens 2.1.3 e 2.2): busca o usuário pelo login ou pelo e-mail no banco de dados, por meio do SQLite embutido no mesmo processo (item 1.7), compara a senha informada com a credencial armazenada e decide pelo sucesso ou pela falha.
 
O resultado do processamento é a resposta HTTP. Em caso de sucesso, o objeto com a identificação do usuário é convertido de volta para JSON e enviado com o código 200; em caso de falha, a resposta leva o código 401 e a mensagem genérica de erro (item 1.4). O Tomcat escreve essa resposta na conexão com o Nginx, que a devolve ao navegador pelo canal seguro, e a thread é liberada para atender outra requisição. Além da resposta, o servidor de aplicação registra em log os eventos do processamento, o que permite acompanhar as tentativas de autenticação e diagnosticar falhas (ANTHROPIC, 2026a).
