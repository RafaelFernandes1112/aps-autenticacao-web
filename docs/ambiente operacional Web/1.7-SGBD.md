## 1.7 Sistema gerenciador de banco de dados

O sistema gerenciador de banco de dados (SGBD) é responsável por armazenar de forma persistente as credenciais registradas e por responder às consultas da aplicação. No ambiente adotado, essa função é exercida pelo SQLite, um mecanismo de banco de dados SQL embutido. Diferentemente de SGBDs cliente-servidor, como o PostgreSQL ou o MySQL, o SQLite não é executado como um processo separado nem recebe conexões pela rede: ele é uma biblioteca que roda dentro do próprio processo da aplicação e lê e grava diretamente um arquivo comum em disco, que contém o banco inteiro, com tabelas e índices. No software projetado, esse arquivo é o auth.db, criado no diretório em que a aplicação é executada, e sua estrutura é definida no modelo de dados da Seção 2 (item 2.2.5).

Na aplicação Java, o SQLite é acessado pelo driver SQLite JDBC, que já traz a biblioteca nativa do SQLite para os principais sistemas operacionais e identifica o banco por um endereço do tipo jdbc:sqlite: seguido do caminho do arquivo, no caso, jdbc:sqlite:auth.db. Na inicialização, o Spring Boot cria um pool de conexões (HikariCP), em que cada conexão corresponde ao arquivo do banco aberto pelo driver, e executa o script schema.sql, que cria a tabela usuario se ela ainda não existir (SPRING, 2026). O SGBD é invocado quando o servidor de aplicação (item 1.6) precisa consultar um usuário: o UserRepository obtém uma conexão do pool e, por meio do JdbcTemplate, executa a consulta parametrizada SELECT id, login, email, nome, senha_hash FROM usuario WHERE login = ? OR email = ?, em que o identificador informado ocupa os dois parâmetros. Na consulta parametrizada, o texto do comando SQL e o valor do identificador são enviados separadamente, de modo que o conteúdo digitado pelo usuário nunca é interpretado como parte do comando, o que impede ataques de injeção de SQL.

Ao receber a consulta, o SQLite a compila em um programa interno, localiza o registro pelos índices das colunas login e email, criados pelas restrições de unicidade dessas colunas, em vez de percorrer a tabela inteira, e lê do arquivo apenas as páginas necessárias. Todas essas etapas ocorrem por chamadas de função dentro do mesmo processo, sem comunicação pela rede, o que torna o acesso rápido. Na configuração adotada, o banco usa o modo de diário padrão do SQLite (rollback journal), que permite várias leituras simultâneas, mas apenas uma escrita por vez, que bloqueia as leituras no momento em que é gravada. Como a API apenas lê a tabela, cujos registros são criados por um sistema externo de cadastro (item 2.2.5), essa limitação não compromete o desempenho do software projetado.

O resultado do processamento é o conjunto de linhas que atende à consulta: uma linha, com o id, o login, o e-mail, o nome e o hash da senha, quando o identificador está cadastrado, ou um resultado vazio, quando não está. O driver entrega esse resultado ao JdbcTemplate, que o converte em um objeto Usuario, e a aplicação prossegue com a comparação da senha e a decisão de autenticação (item 1.6). As transações do SQLite seguem as propriedades ACID, o que garante a integridade dos dados mesmo em caso de falha do sistema ou de queda de energia (ANTHROPIC, 2026d).
