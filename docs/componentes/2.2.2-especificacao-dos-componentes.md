## 2.2.2 Especificação dos componentes

A Tabela 3 especifica os quatro componentes da Figura 5. A Tabela 4 especifica os objetos de dados que circulam entre eles.

Tabela 3 – Especificação dos componentes

| Componente | Responsabilidade | Operações (entrada → saída) | Dependências |
| --- | --- | --- | --- |
| AuthController | Receber a requisição HTTP, validar os campos e converter o resultado em resposta HTTP. | `login(LoginRequest)` → `200` com `LoginResponse`<br>`credenciaisInvalidas(AuthenticationException)` → `401` com `ErrorResponse`<br>`requisicaoInvalida(Exception)` → `400` com `ErrorResponse` | AuthService |
| AuthService | Decidir a autenticação: buscar o usuário, comparar a senha e montar o resultado. | `autenticar(identificador, senha)` → `UserIdentity` ou lança `AuthenticationException` | UserRepository, PasswordEncoder |
| UserRepository | Consultar o usuário por login ou e-mail. | `buscarPorIdentificador(identificador)` → `Optional<Usuario>` | JdbcTemplate, SQLite |
| PasswordEncoder (`BCryptPasswordEncoder`) | Comparar a senha informada com o hash registrado. | `matches(senha, hash)` → `boolean` | Módulo de criptografia do Spring Security |

Fonte: Elaborado pelos autores (2026).

Tabela 4 – Objetos de dados e de domínio

| Classe | Campos | Uso |
| --- | --- | --- |
| LoginRequest | `identificador` (String, obrigatório), `senha` (String, obrigatório) | Corpo da requisição. Campo ausente ou vazio resulta em `400`. |
| LoginResponse | `id` (long), `nome` (String) | Corpo da resposta `200`. |
| ErrorResponse | `erro` (String) | Corpo das respostas `400` ("Requisição inválida") e `401` ("Credenciais inválidas"). |
| UserIdentity | `id` (long), `nome` (String) | Resultado do `AuthService`. Imutável e sem dados sensíveis. O controller o converte em `LoginResponse`. |
| Usuario | `id`, `login`, `email`, `nome`, `senhaHash` | Registro lido do banco. Uso interno, nunca devolvido ao cliente. |
| AuthenticationException | (sem campos próprios) | Sinaliza falha de autenticação sem distinguir a causa (RNF03). |

Fonte: Elaborado pelos autores (2026).

As regras de projeto abaixo se aplicam aos componentes:

1. **Validação de entrada.** O `AuthController` rejeita com `400` o corpo que não seja JSON válido ou que tenha `identificador` ou `senha` ausente ou vazio. Nesse caso o `AuthService` não é chamado. O significado do `400` e do `401` segue a especificação do HTTP (FIELDING; NOTTINGHAM; RESCHKE, 2022).
2. **Normalização do identificador.** O `AuthService` remove espaços nas pontas e converte o identificador para minúsculas antes da busca. Login e e-mail são gravados em minúsculas (Seção 2.2.5).
3. **Erro único.** Usuário inexistente e senha incorreta lançam a mesma `AuthenticationException`, e o controller responde `401` com a mesma mensagem (RNF03).
4. **Tempo de resposta semelhante.** Quando o usuário não existe, o `AuthService` compara a senha com um hash fictício gerado na inicialização (`hashFicticio`). Assim o tempo de resposta não revela se o usuário existe (OWASP, s.d.).
5. **Hash com salt.** O BCrypt incorpora o salt ao hash e usa custo configurável (PROVOS; MAZIÈRES, 1999). Por isso a comparação é feita por `matches`, e o hash nunca é recalculado para ser comparado como texto (RNF02).
6. **Sem registro de senha.** A senha não é escrita em log nem devolvida em nenhuma resposta.
