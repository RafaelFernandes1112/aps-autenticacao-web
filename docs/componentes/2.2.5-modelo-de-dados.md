## 2.2.5 Modelo de dados

A Figura 10 mostra a única tabela que o sistema consulta, `usuario`, no banco SQLite (Figura 4). A Tabela 5 descreve as colunas. Os registros são criados pelo sistema externo de cadastro de usuários, que está fora do escopo (Figura 3). Este projeto só lê a tabela.

Figura 10 – Modelo de dados do usuário. Arquivo: `diagramas/modelo-de-dados.drawio`.

Tabela 5 – Colunas da tabela `usuario`

| Coluna | Tipo | Restrições | Descrição |
| --- | --- | --- | --- |
| `id` | INTEGER | Chave primária, autoincremento | Identificação do usuário devolvida no `200`. |
| `login` | TEXT | Não nulo, único, minúsculas, sem `@` | Identificador alternativo de acesso. |
| `email` | TEXT | Não nulo, único, minúsculas, contém `@` | Identificador alternativo de acesso. |
| `nome` | TEXT | Não nulo | Nome devolvido no `200`. |
| `senha_hash` | TEXT | Não nulo | Hash BCrypt da senha. Contém versão, custo e salt, com cerca de 60 caracteres. |

Fonte: Elaborado pelos autores (2026).

O esquema em SQL é:

```sql
CREATE TABLE usuario (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  login      TEXT NOT NULL UNIQUE CHECK (login = lower(login) AND instr(login, '@') = 0),
  email      TEXT NOT NULL UNIQUE CHECK (email = lower(email) AND instr(email, '@') > 1),
  nome       TEXT NOT NULL,
  senha_hash TEXT NOT NULL
);
```

A consulta do `UserRepository` usa um único parâmetro, nas duas colunas:

```sql
SELECT id, login, email, nome, senha_hash
  FROM usuario
 WHERE login = ? OR email = ?;
```

A restrição de que o login não contém `@` e o e-mail contém garante que um identificador corresponda, no máximo, a um usuário. As restrições `UNIQUE` criam índices em `login` e `email`, que atendem a consulta de autenticação.
